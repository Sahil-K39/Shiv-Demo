# Shiv Shakti Project Architecture and Assessment Report

## 1. Verification Summary

This report was checked against the repository on 2026-05-22. The project is a full-stack commerce and community platform with a decoupled frontend and backend:

- Frontend: Next.js App Router application in `frontend/`, using TypeScript, Tailwind CSS, Framer Motion, Zustand, and Next image optimization.
- Backend: Go service in `backend/`, using Gin, SQLite, JWT authentication, CSRF protection, rate limiting, secure headers, and SMTP-backed transactional email.
- Deployment shape: frontend is Vercel-ready through the Next.js standalone output, while the backend is Dockerized for a Render-style web service.

Key correction from the initial brief: the frontend package currently pins `next` to `16.2.6`, not Next.js 14. The project README also mentions React 19, but `frontend/package.json` currently uses React `18.2.0` while TypeScript types are on `@types/react` 19.

## 2. Technical Stack and Architecture

### Frontend

- Framework: Next.js `16.2.6` with the App Router.
- Language: TypeScript.
- Styling: Tailwind CSS v4 through `frontend/src/app/globals.css`.
- State: Zustand cart store in `frontend/src/store/cart.ts`.
- Media: Next.js `Image` is used across product cards, product details, cart, login, logo, NGO, and landing page views.
- API layer: `frontend/src/lib/api.ts` centralizes calls to the backend and uses `NEXT_PUBLIC_API_URL` with credentials enabled for session cookies.

The app supports storefront browsing, collection pages, product detail pages, login, account, cart drawer UI, NGO page, council page, lookbook, search, and community-style routes.

### Backend

- Language: Go `1.26.3` as declared in `backend/go.mod`.
- Framework: Gin `1.12.0`.
- Database: PostgreSQL in production through `DATABASE_URL`, with SQLite retained as a local fallback through `DB_PATH`.
- Auth: JWT via `github.com/golang-jwt/jwt/v5`, stored in an HttpOnly `shiv_session` cookie.
- Password security: bcrypt with cost `12`.
- Email: SMTP service in `backend/internal/email/email.go`, with mock-mode logging when SMTP env vars are absent. A Resend demo endpoint also exists at `/send-email`.
- Runtime: Docker multi-stage backend build in `backend/Dockerfile`.

The backend exposes REST endpoints under `/api`, serves shared assets from `/assets`, and includes a `/health` endpoint for deployment health checks.

## 3. Core Features Confirmed in Code

### Authentication and Security

- Registration, login, logout, email verification, and authenticated `/api/auth/me` endpoints are implemented.
- JWT authentication accepts the `shiv_session` cookie, with Bearer token fallback.
- CSRF tokens are generated by `/api/csrf-token` and required for cart, checkout, community writes, and admin product mutations.
- Secure headers, CORS, and rate limiting middleware are configured globally.

Assessment note: CSRF tokens are stored in backend process memory. This is fine for a single instance, but a multi-instance deployment should move token/session coordination to shared storage or switch to a stateless CSRF strategy.

### E-Commerce

- Product catalogue tables, seed products, product listing, category filtering, and product admin CRUD exist.
- Cart add, update, remove, and retrieval endpoints exist and are user-scoped.
- Checkout creates an order transactionally, inserts line items, clears the cart, and sends an asynchronous order confirmation email.

Assessment note: checkout now creates `payment_pending` wholesale orders instead of marking unpaid orders as confirmed. Production checkout should still add Stripe/Razorpay payment creation plus webhook verification before orders move to `confirmed`.

### Community and Engagement

- Community post listing, creation, and liking are implemented.
- NGO interest storage exists in the database layer.
- Frontend NGO and council pages exist.

Assessment note: NGO interest submission is now wired through `POST /api/ngo/interest` and the frontend NGO form submits to that endpoint.

### Email System

- Welcome, verification, and order confirmation emails are implemented with HTML templates.
- SMTP is environment-variable driven.
- Mock mode logs email metadata when SMTP configuration is missing.

Assessment note: verification URLs depend on `FRONTEND_URL`; this variable must be set in Render for production verification links to work.

## 4. Deployment Assessment

### Vercel Frontend

Required production variables:

- `NEXT_PUBLIC_API_URL`: public Render backend origin.
- `INTERNAL_BACKEND_URL`: backend URL used by Next rewrites if rewrites are used in production.
- `NEXT_PUBLIC_IMAGE_HOSTNAME`: hostname serving `/assets/**`.

The Next config rewrites `/api/:path*` and `/assets/:path*` to the backend. If the frontend calls `NEXT_PUBLIC_API_URL` directly, CORS and cookie settings must match the frontend domain.

### Render Backend

Required production variables:

- `PORT`: usually supplied by Render.
- `JWT_SECRET`: long random production secret.
- `CORS_ORIGIN`: exact Vercel frontend origin.
- `FRONTEND_URL`: exact public frontend URL for verification links.
- `DATABASE_URL`: managed PostgreSQL connection string.
- `DB_PATH`: local SQLite path for development only.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`: required to leave email mock mode.
- `REQUIRE_SMTP=true`: recommended in production so the backend fails fast instead of silently logging mock emails.

PostgreSQL is now the production path. When `DATABASE_URL` is set, the backend uses PostgreSQL and runs PostgreSQL-compatible table creation. SQLite remains available for local development when `DATABASE_URL` is not set.

## 5. Recent Optimization Milestones

Confirmed optimization work includes:

- Next `Image` usage across major visual components.
- A landing-page comment showing deterministic image choices were introduced to avoid hydration mismatch from `Math.random()`.
- Environment-driven frontend/backend URLs.
- Dockerized Go backend with multi-stage build.

The root-level `Dockerfile` now builds the Go backend from the repository root, so Render can safely use either the root Dockerfile or `backend/Dockerfile` with the backend directory as context.

## 6. Roadmap

Priority recommendations:

1. Integrate Stripe or Razorpay with a pending-order to paid-order lifecycle.
2. Add a one-time SQLite-to-PostgreSQL import if old local data must be preserved.
3. Move CSRF/session coordination away from process memory if backend scaling is planned.
4. Align React and type package versions, then run a clean production build.
5. Add explicit versioned database migrations for long-term schema management.
